# Memcached x86 ASM and SIMD Optimization Opportunities

This document records optimization opportunities in memcached 1.6.45 that can be
addressed with x86-64 assembly or SIMD (SSE/AVX2 and friends). It is grounded in
the compiled code: each opportunity cites a source location and, where useful,
the actual generated assembly captured under `docs/analysis/asm/`.

## Method and environment

- Each compute-heavy translation unit was compiled at `-O3 -march=native
  -ftree-vectorize` with GCC's vectorizer log (`-fopt-info-vec-all`). Assembly is
  in `docs/analysis/asm/<file>.s`; vectorizer notes in `docs/analysis/asm/<file>.vec.txt`.
  Generated by `scripts/gen_asm.py`.
- The build machine's CPU exposes: **SSE4.2, AVX2, BMI2, POPCNT, PCLMULQDQ,
  AES, SHA-NI, VAES**. So SSE2 through AVX2 plus carry-less multiply are all
  available.
- Important build fact: the stock memcached Makefile compiles at **`-O2` with no
  `-march`**. On x86-64 that guarantees only the SSE2 baseline. Anything beyond
  SSE2 (AVX2, BMI2, PCLMULQDQ, hardware CRC in the compiler's own codegen) is left
  on the table unless a file opts in with `__attribute__((target(...)))` and a
  runtime CPUID check, or the whole build raises its baseline.

A recurring theme below: memcached already hand-writes SIMD/ASM exactly where the
authors measured it mattered (hardware CRC, xxHash), and leans on glibc's
SIMD-optimized `memcpy`/`memcmp`/`memchr` elsewhere. The remaining wins are (1)
letting the already-SIMD-capable code actually use AVX2 at build time, and (2) a
few scalar byte-loops that are good vectorization candidates.

## Summary

| # | Opportunity | Location | Current codegen | Proposed | Priority |
|---|---|---|---|---|---|
| 1 | Default hash (XXH3) stuck on SSE2 | `hash.c`, `xxhash.h` | 0 AVX2 insns at `-O2` | Build hash TU with AVX2 (dispatched) | High |
| 2 | Text tokenizer byte-scan for `' '` | `vendor/mcmc/mcmc.c` `_mcmc_tokenize_meta` | scalar per-byte loop | SSE2/AVX2 delimiter scan | High |
| 3 | Base64 encode/decode scalar loops | `base64.c:116`, `base64.c:176` | scalar, not vectorized | Vectorized base64 (SSE/AVX2) | Medium |
| 4 | CRC32C combine uses shift tables | `crc32c.c:160` | 3-way `crc32q` + tables | PCLMULQDQ folding | Low |
| 5 | Key compare in hash lookup | `assoc.c:87,115` | glibc `memcmp` (already SIMD) | Leave as-is / inline small-key fast path | Info |
| 6 | Integer formatting | `itoa_ljust.c` | 2-digit LUT, already optimal | No change | Info |
| 7 | Raise build baseline / runtime dispatch | Makefile / configure | `-O2`, SSE2 only | `-march=x86-64-v3` or dispatch | High |

## 1. The default hash function (XXH3) never uses AVX2 in the stock build

**Where.** `hash.c` selects the hash used for every key. The default is
`XXH3_HASH` (`memcached.c:4735`, `enum hashfunc_type hash_type = XXH3_HASH;`), and
`hash.c` pulls in the full xxHash implementation with `#define XXH_INLINE_ALL`.
`assoc_find`, insert, and delete all call this on the request path, so it runs at
least once per key per operation.

**Evidence.** xxHash picks its vector backend from compile-time macros
(`__AVX2__`, `__SSE2__`, ...). On x86-64 `__SSE2__` is always set but `__AVX2__`
is not unless you pass `-mavx2`. Compiling `hash.c` three ways and counting
vector registers in the output confirms it:

```
flags=-O2                    ymm(AVX2)=0    xmm(SSE)=48
flags=-O2 -mavx2 -mbmi2      ymm(AVX2)=67   xmm(SSE)=2
flags=-O3 -march=native      ymm(AVX2)=67   xmm(SSE)=2
```

At the shipped `-O2`, XXH3 emits **zero** AVX2 instructions and runs its 128-bit
SSE2 path. With AVX2 enabled it processes 32 bytes per step instead of 16, which
roughly halves the mixing loop iteration count for larger keys and is a
measurable win once keys exceed ~16 bytes.

**Proposed.** Do not just add `-mavx2` globally (it would fault on older CPUs).
Instead use xxHash's supported dispatch: build with `xxh_x86dispatch.c` /
`XXH3_dispatch` so the correct backend (scalar/SSE2/AVX2/AVX512) is chosen at
runtime via CPUID. If a fixed deployment target is known, raising the baseline
(see #7) is simpler. Either way, gate AVX2 behind a runtime check for
portability.

## 2. Text-protocol tokenizer scans one byte at a time for spaces

**Where.** `vendor/mcmc/mcmc.c`, `_mcmc_tokenize_meta`. Every ASCII/meta command
is tokenized here (`proto_parser.c` calls `mcmc_tokenize` for meta, mset, gat,
etc.). The core is a per-byte loop:

```c
while (n != end) {
    if (*n == ' ') {
        ... record token ...
    }
    n++;
}
```

The authors already left a note in the source that long tokens could use
`memchr` to skip to the next space, and the `max`-token path already falls back to
`memchr(s, ' ', end - s)`.

**Proposed.** Replace the hot scan with a SIMD delimiter search: load 16 (SSE2)
or 32 (AVX2) bytes, `PCMPEQB` against a broadcast `' '`, `PMOVMSKB` to a bitmask,
and use `tzcnt` (BMI1) to jump to the next delimiter. This is exactly what glibc
`memchr` does, so the lowest-risk version is to restructure the loop around
`memchr` for the token body and keep the per-byte logic only at token starts (to
fill `metaflags`). Commands are short (bounded by `TOKENIZER_MAXLEN`), so the win
is in cutting per-byte branch mispredicts on multi-field meta commands.

**Caveat.** The metaflags bookkeeping (`*s > 64 && *s < 123`) happens at each
token start, not each byte, so it does not block vectorizing the *scan*. Preserve
the early `MCMC_NOK` validation behavior exactly.

## 3. Base64 encode and decode are scalar

**Where.** `base64.c`. `base64_encode` (loop at `base64.c:116`) processes 3 input
bytes to 4 output chars per iteration; `base64_decode` (loop at `base64.c:176`)
does the reverse plus a validation pre-scan (`base64.c:158`). Used for
base64-encoded keys in the meta protocol and LRU crawler
(`proto_text.c:632,655`, `proto_parser.c:498`, `crawler.c:418`).

**Evidence.** The vectorizer explicitly gives up:

```
base64.c:116:21: missed: couldn't vectorize loop
base64.c:116:21: missed: not vectorized: number of iterations cannot be computed.
```

**Proposed.** Use a known vectorized base64 (Muła/Lemire style): with SSE/AVX2 the
encode is a shuffle to spread 3-byte groups across 4 output lanes, a few
multiplies/shifts to isolate 6-bit fields, and a range-compare table to map values
to the alphabet; decode is the inverse with a validation mask. This is typically
4x-10x faster than scalar for buffers more than a few dozen bytes. Keys here are
small (<=250 bytes) so the absolute win per call is modest, but it is a clean,
self-contained function with a well-known correct implementation. Runtime dispatch
again required.

## 4. CRC32C already uses hardware `crc32q`; PCLMULQDQ could replace the combine tables

**Where.** `crc32c.c:160` `crc32c_hw`. This is the classic Mark Adler
implementation: it runs three independent `crc32q` instructions over interleaved
8 KB (`LONG`) and 256 B (`SHORT`) blocks to hide the 3-cycle latency, then stitches
the three partial CRCs together using precomputed shift tables
(`crc32c_long`/`crc32c_short`, `crc32c.c:151-152`). Selection between hardware and
software is done once via CPUID/`getauxval` (`crc32c.c:267-361`). CRC32C is used
by extstore and the restart/metadata paths, not the main get/set hot path, so
this is low priority.

**Proposed.** On CPUs with PCLMULQDQ (present here) a carry-less-multiply folding
scheme can fold multiple 16-byte lanes per iteration and combine them without the
`crc32c_long`/`crc32c_short` lookup tables, which both removes the table init
(`pthread_once` + `crc32c_zeros`) and tends to be faster on modern cores for large
buffers. This is a bigger change for a cold path, hence low priority; the existing
3-way `crc32q` is already good.

## 5. Key comparison in hash lookups is already SIMD via glibc

**Where.** `assoc.c:87` (`assoc_find`) and `assoc.c:115` (`_hashitem_before`)
compare keys with `memcmp` after a cheap `nkey == it->nkey` length gate. glibc's
`memcmp` is already AVX2-optimized and dispatched at runtime.

**Assessment.** No SIMD change needed. The one micro-opportunity is that keys are
short and the length gate already filters most mismatches, so an inlined
small-fixed-size compare (e.g. 8/16-byte unaligned loads for the common short-key
case) could shave the `memcmp` call overhead. This is a minor, easy-to-get-wrong
change; treat as informational.

## 6. Integer-to-ASCII is already optimal

**Where.** `itoa_ljust.c`. It converts two digits at a time from a 200-byte LUT
and stores them with a 2-byte `memcpy`, avoiding per-digit division. The
vectorizer report shows nothing to vectorize (`not_vectorized=0`) because the
algorithm is inherently data-dependent and already near the practical floor for
the small integers memcached formats. No change recommended.

## 7. Build-level: raise the ISA baseline or add runtime dispatch

**Where.** The Makefile compiles at `-O2` with no `-march`, so the whole binary
targets the SSE2 baseline. This is what caps opportunity #1 and limits glibc's
ifunc-selected `memcpy`/`memcmp`/`memchr` to their SSE2/generic variants on the
call sites the compiler inlines.

**Proposed, two options:**

1. **Raise the baseline.** Add a `configure` option to build with
   `-march=x86-64-v3` (AVX2 + BMI2 + FMA, supported by essentially all server
   CPUs since ~2015). This unlocks #1 for free and lets the compiler autovectorize
   more loops. Tradeoff: the binary will `SIGILL` on pre-Haswell/pre-Excavator
   hardware, so it must be opt-in.
2. **Runtime dispatch (portable).** Keep the SSE2 baseline but compile the
   specific hot functions (XXH3 backend, a vectorized base64, the tokenizer scan)
   in multiple ISA variants with `__attribute__((target_clones("default,avx2")))`
   or GNU ifunc, selected by CPUID at load time. This keeps a single portable
   binary while getting AVX2 where present. This is the pattern memcached already
   uses for CRC32C selection, so it fits the codebase.

## Priority ordering

1. **#1 / #7** together: make the default hash use AVX2 via dispatch. Highest
   value because it is on every request and is verified to be leaving AVX2 unused.
2. **#2** tokenizer SIMD scan: on every text command, low risk if built around
   `memchr`.
3. **#3** vectorized base64: self-contained, meaningful for meta base64-key
   workloads.
4. **#4** PCLMULQDQ CRC: only if extstore/restart CRC throughput becomes a
   bottleneck.

## Reproducing

- `python3 scripts/gen_asm.py` regenerates all assembly and vectorizer logs.
- The XXH3 AVX2 comparison in #1 is reproduced by compiling `hash.c` at `-O2`
  versus `-O2 -mavx2 -mbmi2` and counting `%ymm` registers in the assembly.
